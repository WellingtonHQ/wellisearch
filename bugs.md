## Field report items

1. **`search_web` results show `Title: <url>`** — the first test returned `Title: https://www.databricks.com/blog/what-is-pgvector` instead of a real page title. The bulk fetch *does* have a `Title:` field (e.g. "PostgreSQL 18.6 Documentation"), so the search pipeline is falling back to the URL when it has no title. Worth checking whether provider results (Tavily returns titles) and/or stored `pages.title` are being threaded into the `results` block.
   - **Status: resolved — no code change needed.** Title threading is intact end-to-end: provider adapters map API titles onto the canonical `Result`, local hits come from `fn_search_local` (`p.title AS title`), and both renderers fall back to the URL only when the title is genuinely missing. Real page titles have been stored at crawl time since v1.1 (e4d18bb). Residual cases are legacy NULL-title rows, which self-heal: `index.store_page` backfills via `COALESCE(%s, title)` on re-crawl, and ead5eb3 now derives a title from the fit-markdown at crawl time so new pages stop being stored with a NULL title (see item 3).
2. **Default strategy mismatch** — my single `fetch_page` call (no strategy specified) was truncated with `strategy=head`, but the plan default is `FETCH_DEFAULT_STRATEGY=smart` [1]. Either the server default is `head`, or `fetch_page` is intentionally `head`-based — worth a one-line check in the config to make the two consistent.
   - **Status: not a bug — by design.** A single `fetch_page` has no budget allocation, so its (intentional) head-trim carries the fixed `[truncated — N chars omitted, strategy=head]` marker specified for it in BLUEPRINT §7; `FETCH_DEFAULT_STRATEGY=smart` governs `fetch_pages`' shared-budget allocation only. Docs (`docs/api.md`) already describe both behaviors.
3. **Title extraction picks nav links on some pages** — the Databricks page came back with `Title: [Skip to main content](...)` (a skip-link anchor, not the article title). A small "prefer `<h1>`/`<title>` over first link" heuristic in the crawler would fix that class of issue.
   - **Status: fixed — ead5eb3.** The shared `title_from_markdown()` heuristic lives in `crawl/extractors/base.py`: first H1, else the first clean line (pure markdown-link lines and symbol-only lines like `---` are skipped), capped at `TITLE_MAX_LEN`. `crawler.fit_markdown` uses it as a last resort so crawled pages store a derived title instead of NULL, and `fetch._resolve_page` reuses the same helper for legacy rows. Covered by the `title_from_markdown` section in `tests/test_extractors.py`.
4. `search_web` via the owui call should return pure markdown the same way as `fetch_page` does. Right now it is returning a JSON object which does not show well on the owui interface.
   - **Status: resolved — no longer applies.** Both surfaces default to Markdown: the MCP tools render the search document by default since v1.0 (d413383), and the REST handler resolves `format` with an explicit `format` param winning over the header (`serialize.resolve_format`) — JSON only comes back when a client sends `format=json` or `Accept: application/json`. The OWUI spec (`owui/openapi.json`) documents Markdown as the default. If OWUI ever shows a JSON object, it is opting in client-side (header or explicit param), not a server defect.

## PR Review Notes

Findings (highest priority first)
- [Warning] src/wellisearch/crawl/engine.py:21-34 - The per-tier backstop is shorter than the browser tier's worst-case budget, so a legitimate slow crawl is cancelled by asyncio.wait_for (engine.py:59) before it can finish. Fast-lane browser: backstop is CRAWL_TIMEOUT_S (45s) but the tier's worst case is goto (45s) + settle (2s) + network_idle (15s) = 62s. CF-lane browser: backstop is CRAWL_CF_TIMEOUT_S * 2 (600s) but the tier's worst case is goto (300s) + settle + network_idle + the full challenge loop (300s budget) + Walmart recovery (300s + settle + wait) ≈ 923s. Derive the backstop from the tier's actual worst-case budget (goto + waits + challenge budget + recovery) instead of a flat timeout.
  - **Status: resolved in v1.5 — 1c7b558.** `engine._tier_backstop` derives the per-tier deadline from each tier's `worst_case_s(policy)`; the browser, stealth, and http tiers all implement it (goto + settle + network_idle when waited for + full challenge-loop budget on CF + Walmart recovery), so a legitimate slow crawl is no longer cut off by a flat timeout.
- [Warning] src/wellisearch/crawl/extractors/amazon.py:17 - amazon.py has a top-level from bs4 import BeautifulSoup and bestbuy.py:37 imports lxml, but neither beautifulsoup4 nor lxml is declared in pyproject.toml. The top-level import is a hard dependency — if bs4 is not a transitive dep of a declared package, importing the extractors package fails with ImportError on a clean install. Add beautifulsoup4 and lxml to the dependencies list in pyproject.toml.
  - **Status: resolved.** `pyproject.toml` declares both hard deps (`beautifulsoup4>=4.12`, `lxml>=5.0`); a clean install now imports the extractors package without ImportError.
- [Warning] src/wellisearch/fetch.py:310 - The on-demand fetch path never routes ChallengeDetected to the CF lane. When fetch_page/fetch_pages hits a bot-wall in the fast lane, ChallengeDetected propagates as a generic failure (caught by except Exception in _resolve_all, fetch.py:352) and the URL is not enqueued to the CF lane. A bot-walled URL fetched on-demand therefore always fails, while the worker path (worker.py:195) routes the same URL to the CF lane and succeeds. Catch ChallengeDetected in the fetch path, route the URL to the CF lane (e.g. db.queue_route_to_cf), and fail gracefully.
  - **Status: resolved in v1.5 — 1c7b558.** `fetch._resolve_page` catches `ChallengeDetected`, enqueues/routes the URL onto the CF challenge lane (`db.queue_enqueue(url, "fetch", lane="cf")` falling back to `db.queue_route_to_cf`), then fails gracefully with a descriptive `CrawlError` — so the worker's CF drain gets the chance to solve the challenge and index the page.
